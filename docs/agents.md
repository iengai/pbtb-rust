# The agents

Two workflows run a model on this repository without a person at the keyboard: `incident-diagnose` (read-only, answers an Incident issue) and `issue-fix` (writes a fix, opens a PR). Both drive Claude Code headless (`claude -p`) on a checkout, so the model works with the harness this repository is written for: `CLAUDE.md` and `AGENTS.md`, the skills, the agents and the hooks under `.claude/`. The model is whatever the Anthropic-compatible endpoint serves: DeepSeek's `deepseek-flash` by default (`ANTHROPIC_BASE_URL` / `ANTHROPIC_MODEL`, from the repository variables `LLM_ANTHROPIC_BASE_URL` / `LLM_MODEL` and the secret `LLM_API_KEY`). The harness version is pinned in both workflows (`@anthropic-ai/claude-code@2.1.263`); a release does not change what a run can do until someone moves the pin. Where each runs and how to dispatch one is in the triage skill's component map; this leaf is for changing them. Sessions on the workstation act under their own GitHub identity: [Local agents](#local-agents).

## What each agent may do

The shared module `scripts/ops/claude_harness.py` builds the harness environment, writes the settings file and provides the hook; each script owns its whitelist and rules.

| | `diagnose_issue.py` | `fix_issue.py run` |
|---|---|---|
| Read / Grep / Glob | inside the checkout only | inside the checkout only |
| Bash | `git log\|show\|blame`; `pbtb_ops.py bot-status\|deploy-audit\|lambda-logs` with validated arguments; `diagnose_issue.py sentry ID` | `cargo test\|check\|clippy\|build\|fmt` with plain arguments; `git diff\|status\|log\|show\|blame`; the gate; `python -m py_compile\|unittest\|doctest`; `python -c` |
| Edit / Write | none | any path not on the deny list (workflows, terraform, hooks, the settings file, the gate, the scripts behind the intake / diagnose / fix workflows and their shared harness module, dependency manifests, build scripts, `.devcontainer/`, `.gitignore`, `.git`, `.cargo`, `AGENTS.md`, `REVIEW.md`) |
| Web, subagents, tasks | none | none |
| Credentials in the environment | the model key; the `gh-diagnose` role's (read-only, for the ops probes); the Sentry token | the model key only: the GitHub token leaves before the harness starts |

The hook (`<script> hook`, wired through the settings file the script writes) decides every tool call and logs every Bash command with its exit code and output to `runs.jsonl`; the "Harness trail" step of each workflow prints the commands, and the artifact carries them. What leaves a run (the answer, the trail, the log) has the model key, the AWS secret and the Sentry token blanked. A hook that cannot decide denies. The whitelist is a scope bound; the safety bounds are which credentials are in the environment and the deny list re-applied to the staged paths in `publish`.

Refusals worth knowing when reading a trail: `ls`, `grep`, `find` (Read / Grep / Glob do that); a pipe, `&&`, `;`, a redirection, `$(…)`; a `--profile` or an environment prefix on an ops probe; any command with a line break (the diagnose agent); `git blame --contents`, `--output`, a `..` path segment; a Read outside the checkout (`/proc/self/environ`, the cargo registry).

## Rules the model gets

Each script appends a `RULES` string as the system prompt: the answer shape the script parses, the whitelist in words, and the habits seen twice. That string is the layer of rules the agent has loaded for every run, whatever the checkout it works on. A habit seen once is a `[cat:agent-habit] Lesson:` line in the run's PR body or comment (docs/conventions.md § Issues); seen twice, it goes into `RULES`, and nowhere else.

## Trying a change

- `gh workflow run issue-fix.yml --ref <branch> -f issue_number=<n> -f dry_run=true` runs the model and the gate on the branch and prints the PR as `run` sees it (the tier hold on what agents load is `publish`'s); nothing is pushed or commented. A real fix runs on `main` only.
- `gh workflow run incident-diagnose.yml --ref <branch> -f issue_number=<n> -f dry_run=true` prints the comment in the log. Off `main` there is no AWS side: the `gh-diagnose` role trusts `refs/heads/main` alone, so the OIDC step is skipped and the ops probes answer with the missing credentials.
- The local `claude` CLI is a different login from the one CI uses; the scripts are tried in CI, not on a workstation. The offline tests of the scripts drive the real hook subcommand with a fake harness; the tests under `scripts/ops/tests/` (the trust rule below among them) run in the verify gate.

## Publishing

`issue-fix`'s second job runs no model code: it re-derives the tier from the issue, applies the patch on `fix/issue-<n>`, opens the PR with the secret `FIX_PUBLISH_TOKEN` (a member's fine-grained token, so the PR's own checks run and a merge closes the issue) or, without it, the repository token (the run waits for a maintainer's approval and a merge closes nothing). A merge tier is held at "open a PR" when the issue's author is outside the repository (the local agent App counts as inside, below), and when the patch touches `.claude/**` or `docs/**`: a change to what agents load is read by a person before it merges.

## Local agents

A Claude Code session on the workstation acts on GitHub as the App `pbtb-local-agent` (`pbtb-local-agent[bot]`), owned by the repository owner and installed on this repository only, never as the person whose `gh` keyring is on the machine. `scripts/ops/agent_identity.py` owns it; its docstring has the mechanism.

- **Setting up a machine.** `agent_identity.py app-url` prints the URL that creates the App and the steps after it: the owner creates it, generates its private key and installs it on this repository. `setup --app-id N --key <pem>` moves the key to `~/.config/pbtb-agent/`, records the App and writes the identity env into this checkout's `.claude/settings.local.json`; `env` writes the same env into another checkout (a worktree without it), `env --remove` takes it out. The owner sets the repository variable `LOCAL_AGENT_USER_ID` to the bot user id `setup` prints. `status`, run from a session, checks the key, the installation's permissions, the token, and the checkout's and the session's env (an inherited `GH_TOKEN` or `GITHUB_TOKEN` fails it: gh prefers them over `hosts.yml`), and exits 1 when one does not hold; `LOCAL_AGENT_USER_ID` it cannot read, so it prints the command that confirms it.
- **What it may do.** Contents, pull requests, issues, actions and workflows: write; checks and statuses: read. It pushes, opens and merges PRs, files and labels issues, dispatches workflows and changes workflow files. Secrets, variables and administration are not granted: `gh secret`, `gh variable set`, rulesets and repository settings stay with the owner. The reach is wider than the list: a workflow the App pushes can read every repository secret, and once merged to `main` it can assume the main-only AWS roles.
- **How a session gets it.** The env sets `GH_CONFIG_DIR` to `~/.config/pbtb-agent/gh` (and `GH_TOKEN` / `GITHUB_TOKEN` empty), replaces git's credential helpers with `agent_identity.py credential`, and makes the bot the commit author and committer, so plain `gh`, `git push`, `git commit` and the scripts that call `gh` act as the bot. The `PreToolUse` hook `agent_identity.py refresh` keeps `gh/hosts.yml` holding an installation token with at least 50 minutes left, or a placeholder when none can be minted. The file is never absent and its token never empty: gh 2.95 falls back to the keyring, which holds the person's token, from `gh auth git-credential` when the file is absent and from `gh api` when `oauth_token` is empty.
- **What the hook refuses.** `guard-shell.py` refuses `gh auth token|login|logout|switch|refresh|setup-git`, `gh auth status --show-token`, `git credential` and credential helpers run or set by hand, `gh secret` and `gh variable set|delete`, setting or unsetting the identity env, any path into `~/.config/pbtb-agent`, and, in a session without the identity env, `gh`, `git push` and `git commit`; `settings.json` denies the Read tool the same directory. A guardrail, not a boundary: any process of the workstation user can read the key, a script that runs `gh` itself is not seen by the hook (`nat_rebuild.py` refuses to dispatch from a session without the identity env), and a tool that does not run Claude Code hooks (Codex) is not guarded.
- **Rotating or revoking.** Generate a new key on the App's page, run `setup` again with it, then delete the old key there; to revoke, suspend or uninstall the App. A lost key leaves the placeholder at the next tool call: commands fail, none acts as the person.
- **Trust in the CI agents.** GitHub never reports an App as a member (`CONTRIBUTOR` or `NONE`), and a bot's login reads `x[bot]` over REST but `x` over GraphQL, a name any user can register. So `fix_issue.py` (the tier and the comments that reach the model) and `incident-diagnose` admit the local agent by numeric user id, the variable `LOCAL_AGENT_USER_ID`; unset, it counts as an outsider.
